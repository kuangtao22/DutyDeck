# 编排工厂场景设计

工厂要解决的是一件事：**把"交给模型做"的环节做成可训练、可交付的场景**。它不负责复刻 app 的整条管线 —— 那是 app 自己的事。

本 Skill 指导**场景设计、试跑与优化对比**。真正的读取、试跑、写草案、写虚拟接入由 `factory_*` 工具完成；采纳、导出、删除场景由人在右侧「工厂」面板完成，你不做也不提议代做。

## 什么时候使用

- 用户说「把某某业务做成一个 agent 能力 / 场景 / 工作流」。
- 用户说「这段提示词我想反复调」「把这个环节交给模型」。
- 用户提到「编排工厂」「提示词工厂」「能力包」「导出给另一个项目用」。
- 用户要求把项目里**已经存在**的流程改造成可训练的场景。

不要强行转入工厂：用户只是让你改代码、写一次性文案、做一次分析时，按普通任务处理。

## 核心口径：只编排模型必须做的那部分

逐环节问四个问题，答案决定它进不进场景：

1. **这一步是否由模型决定「要不要做、以及用什么参数做」？** 是 → 候选步骤（`llm` / `extract`）；不是 → 下一步。
2. **它是不是确定性代码？**（读文件或数据库、解析、切分、核对、去重、排序、写库、拼装返回） 是 → 它是**边界**，不是流程。
3. **边界在模型之前还是之后？** 在模型之前 → 作为**输入契约**由项目给进来；在模型之后 → 作为**输出的消费方**由项目在拿到模型输出后接出去。
4. **这一步里既有模型判断又有确定性处理？** 拆开：模型只负责产出结构化结果，确定性处理留在 app 侧消费它。

一句话判据：**模型决定要不要做 / 怎么做的，才是场景的一部分。**

## 反例（真实发生过）

用户的项目里「小说角色提取」被设计成 4 步：构建带段落引用的批次正文 → 扫描人物候选 → 逐条证据落锚 → 与既有角色合并为候选变更集。其中 3 步是项目代码，只有「扫描人物候选」需要模型判断；输出声明的还是 app 的产物（合并变更集、落锚报告）。

后果：这 3 步在工厂里只能用桩替代，桩给空值 → 跑出「完成 + 约束通过」却什么也没证明；提示词根本训不动；整个场景也交不出去。

正确形状：输入 `corpusText`（app 构建好的正文）、1 步 `extract`（扫描候选）、输出 `characters`；落锚核对与合并预览留在 app。

## 设计步骤

1. **先读项目**：真实的接口定义、数据模型、既有实现。不要凭用户的描述猜字段名与结构 —— 猜错会在导出、接入时才暴露。
2. **画边界**：把用户说的这条流程切成「模型段 / 确定性段」，把切法讲给用户听（哪几段不进场景、为什么）。
3. **写定义**：输入契约 → 步骤与提示词 → 输出声明 → **每个模型步骤自己的评审标准** → 模型槽位。步骤标题写明"这一步做什么判断"，提示词写清判定口径与输出形状。
4. **判据要可检查**：每个 `llm` / `extract` 步骤都要在 `stepAcceptances[stepId]` 下写自己的判据、评审提示词和指标；不要把不同步骤的标准塞进一套顶层口径。判据写成"能被判定"的句子，例如"每个候选名称都能在正文里逐字找到""每轮不超过 6 人""不出现正文里没有的角色"。写成"更准确""更自然"这类形容词等于没有判据。评审提示词说明证据如何核对、指标的公式/单位/阈值、何时无法判断。不要擅自给缺少人工标注的场景定义不可计算的准确率。顶层 `acceptance` 仅为旧场景兼容保留。
5. **模型槽位**：不要在定义里留 `createEmptySceneDefinition` 的模板模型名；按项目实际会用的模型写，并说明消费方可以在接入时覆盖。
6. **出草案**：用 `factory_prepare_draft` 签发快照，向用户说明「改了什么」与「为什么这样切边界」。**草案不生效**，采纳由人做。

## 迭代方式

提示词好不好，只能靠**真实输入**跑出来看。你自己就能跑，不必等人：

1. `factory_get_scene` 看这一步声明了哪些输入槽（`steps[].inputs` 的键就是变量名）。
2. `factory_run_step({ sceneId, stepId, input })` 跑这一步，输入使用任务范围内可用且具有代表性的内容。运行成功后工厂会自动按该步骤自己的 `stepAcceptances[stepId]` 调用评审模型；返回里直接带：渲染后的完整提示词、模型原始返回、解析结果、约束不通过的原因、耗时，以及只覆盖当前步骤的 `review` 内容评审报告。评审提示词留在工厂，不必给应用流程增加“评审步骤”。
3. `factory_list_runs({ sceneId, kind: 'step' })` 看这一步的历次尝试，对比上一版与这一版。
4. 先读 `review.criteria` 的问题与证据、`review.metrics` 的计算依据，再参考 `review.suggestions` 提出修改；模型评审是辅助判断，仍须核对证据。一次只改一个明确问题，说明改哪一句、预期改善哪个判据。整链候选必须按下面的优化闭环验证，不能把未修改的当前版本重跑当成候选验证。

## 优化闭环：在当前会话提出，采纳前验证

1. `factory_get_scene` 读取当前场景与草案，`factory_list_runs` 读取用户指定的运行；`factory_list_tasks` 复用本场景保存任务，不让用户重复粘贴，不另开会话。结合当前项目判断是提示词、步骤衔接、样本还是评审问题。`review.status=failed` 是评审自身失败：先检查评审标准与报告协议，不能根据它改业务提示词或宣称质量不合格。
2. 用 `factory_prepare_draft` 展示改动与原因，经过既有批准流程再 `factory_apply_draft` 写入候选草案。不能先采纳再验证。没有草案时先完成写草案；只有 prepare 尚未 apply 时无法试跑。
3. 再读场景，固定 `expectedVersion=currentVersion`、`expectedDraftCreatedAt=draft.createdAt` 与 `expectedDraftDefinition=draft.definition`。选取用户本轮授权的代表任务，每条两版使用同一份输入、相同模型配置和同一套评审标准；同一对共享一个唯一 `comparisonId`。先调用 `factory_run_scene({ sceneId, input, target: 'current', expectedVersion, comparisonId, comparisonRole: 'baseline' })`，再调用 `factory_run_scene({ sceneId, input, target: 'draft', expectedVersion, expectedDraftCreatedAt, expectedDraftDefinition, comparisonId, comparisonRole: 'candidate' })`。每次都会执行流程与自动评审，按明确任务数顺序运行，禁止无界自动迭代。
4. 对比 `definitionSnapshot`、输出、逐条判据及证据、实际模型、执行与评审耗时。只把明确的未通过→通过计为修复，通过→未通过计为退化；缺少证据、null、评审失败、占位桩不能算优化成功。至少复测其他具有代表性的已保存任务，防止只针对一篇正文调参；只有一个样本时说明尚未证明泛化。版本或草案身份不符时停止并重新读取，不沿用旧对比结论。
5. 向用户展示改善、新增问题、尚未确认的部分和改动原因，让用户在「运行 → 优化对比」查看两版后采纳。草案仍未生效，不代替用户采纳，不把试跑结果当成已交付能力包。

**标准变更单独处理：** 候选与当前标准不同会拒绝优化对比。确需修正标准时，单独说明理由并让用户确认；先采纳标准修正，再把旧/新业务提示词分别放在统一标准下重新验证。不能用旧标准的分数直接比较新标准，也不能放宽标准制造“优化成功”。评审提示词只定义判定口径；报告 JSON 协议由工厂提供，不另外要求模型输出冲突的字段。

使用纪律：

- 试跑**不改场景、不推版本、不导出**，只写一条运行记录；要真正生效仍然只有一条路 —— 出草案 → 人采纳。
- 看结果时三个轴分开读：`status` 是完整性（跑完没有），`valid` 是约束（输出合法不合法），`review` 是整链汇总的内容质量；`stepReviews[stepId]` 才是每个流程步骤的具体评审证据。`steps[].status` 只说明每步执行情况。**"跑完了"不等于"结果可信"**。
- `review.status=succeeded` 表示评审完成，不代表达标；还要看 `review.passed`。`false` 是未达标，`null` 是缺少依据；`failed` 是评审自身失败，`skipped`/缺失是未评测。单步报告只覆盖当前步骤，不能宣称整个场景达标。缺少评审标准时先提出标准草案，不能虚构结论。
- **不要为了"让整条链跑通"去绑虚拟接入**：桩是链式验证的兜底，空占位值会让没有验证过的东西长出绿色徽标。

## 权限边界

- 你能：读取场景、版本、任务、运行记录与虚拟接入；在用户要求的测试范围内试跑当前版或草案。写草案、写虚拟接入沿用人工批准流程。
- 你不能，也不要提议代做：采纳、回滚、导出能力包、删除场景。
- 拿到写入结果后，不要声称"已经改好了" —— 草案还没有生效。
