# 运维版本发布完整性评估

日期：2026-10-15

状态：根据用户新增的数据库字段变更要求形成的方案建议；尚未接入真实发布或迁移执行。

## 1. 结论

发布应管理一份完整的发布计划：应用产物、配置、数据库迁移、数据处理、依赖服务、流量切换、验证以及恢复条件。Git tag/commit 用于追溯源码，不能独立代表可部署、可恢复的版本。

数据库迁移应是一等发布阶段，不能隐藏在“数据库兼容性通过”里，也不应让 Agent 在生产环境临时拼接 ALTER TABLE 后直接执行。优先接入被部署项目已有的迁移工具与迁移文件；DutyDeck 负责绑定目标、预检、编排、确认、观察和记录。

需要区分三种恢复：

- **应用回退**：恢复已保留的镜像和兼容配置，数据库保持当前状态；前提是旧应用能正确读写当前结构与数据。
- **迁移向前修复**：增加一条新的、可审查的迁移，修复已经发生的结构或数据问题；不修改已执行迁移的正文或校验值。
- **数据恢复**：通过经过验证的备份、快照或时间点恢复纠正数据损坏；涉及停写、恢复范围、恢复时间和新增数据处理，是独立恢复任务。

不能把“存在 down 脚本”“有备份文件”或“旧镜像还在”直接展示为可回退。

## 3. 数据库变更如何分类

| 变更类型 | 需要核对的影响 | 推荐执行方式 | 回退限制 |
| --- | --- | --- | --- |
| 新增可空字段/新表 | ORM、无列名 INSERT、SELECT *、默认值、表大小、引擎版本 | 尽量采用向后兼容的扩展迁移，在新代码依赖字段前完成 | 旧应用经兼容验证后可回退，新增结构可暂时保留；“新增”不等于绝对安全 |
| 新增 NOT NULL、唯一约束或外键 | 现存空值、重复值、孤儿记录、扫描与锁等待 | 分离新增、补齐、校验、收紧约束的步骤 | 收紧约束后旧写入可能失败，必须重新验证旧版本 |
| 删除字段/表 | 所有调用方、离线任务、报表、外部集成及数据保留要求 | 先停用并保留一段回退窗口，确认依赖清零后另一次发布清理 | 数据可能不可恢复；旧应用通常不能直接回退 |
| 字段改名 | 旧代码、旧消费者和历史消息是否仍使用旧名 | 新字段 + 兼容读写 + 数据回填 + 切读 + 延后删除旧字段 | 不能直接假设 RENAME 后旧代码仍能工作 |
| 字段类型、长度、精度、字符集变化 | 截断、溢出、比较语义、排序规则和表重写成本 | 验证数据分布，必要时使用新列转换并分阶段切换 | 缩窄或有损转换不能靠反向 ALTER 恢复原值 |
| 新增/删除索引 | 表规模、写入放大、临时磁盘、锁和查询计划 | 按目标引擎/版本选择支持的方式，设置锁等待与执行预算 | 索引移除会改变性能；“在线”不代表完全没有锁 |
| 历史数据回填/清洗 | 影响范围、并发写入、触发器副作用、复制延迟 | 独立分批任务，按稳定主键断点续跑、限速、条件更新与校验 | 要保证不会覆盖新写入；不可把半完成的任务标成全量完成 |
| 枚举/业务状态含义变化 | 旧应用能否理解新值、旧消息重放及报表统计 | 同步检查程序模型、读写兼容与业务不变量 | 即使表结构完全相同，旧应用也可能不能回退 |
| 数据库引擎升级/数据卷迁移 | 存储格式、插件、驱动、备份恢复、可用时间 | 独立维护计划、演练和明确的停写/切换方案 | 不纳入普通应用版本的一键回退，不通过更换数据库容器镜像降级 |

实际执行成本与事务能力取决于引擎、版本、操作和数据规模。不能统一宣称 DDL 支持事务回滚，也不能把生产库“执行后 ROLLBACK”当成无副作用测试。特别是 MySQL DDL，现有项目规范已经明确不承诺事务回滚。

### 例：把 name 改成 display_name

1. 发布 A 的迁移新增 `display_name`，保留 `name`，先保持可空或其他兼容条件。
2. 发布兼容代码：双写，并允许从旧字段回读。等待旧写入进程退出，或提供能覆盖混合版本写入的同步措施。
3. 分批补齐历史数据，使用条件更新或版本条件避免覆盖并发新值，核对一致性。
4. 发布 B 切换读取；继续保留旧字段和兼容写入。此时明确可退回的目标应是已验证的兼容版本 A，不能泛化为任意旧版本。
5. 回退窗口结束，确认所有应用、任务、报表和外部调用方已停止依赖旧字段，再通过独立变更删除 `name`。

数据库与新旧应用会在一段时间内共存，兼容性需要覆盖读、写和真实业务语义，不能只比较一个 schema 整数。

## 4. 每次发布还应检查哪些内容

| 范围 | 必须回答的问题 | 对用户的影响 |
| --- | --- | --- |
| 构建与产物 | 对应哪个 commit，CI 是否通过，镜像 digest/来源是否可信，CPU 架构是否匹配，旧产物是否仍可取回？ | 防止版本名相同但内容不同；测试环境验证的产物应原样提升到生产 |
| 配置与秘密 | 环境变量新增/删除/改值是什么，凭据引用是否可用，外部配置或功能开关是否变化？ | 镜像回退不一定能恢复已撤销密钥；秘密只引用，不交给模型或写入日志 |
| 数据库与数据 | 哪些库/schema/租户受影响，迁移起点是否一致，是否有手工改库或已执行脚本被修改？ | 应用服务器身份不等于数据库身份，必须单独绑定真实数据库目标 |
| 关联服务与接口 | API、RPC、事件结构和 SDK 是否兼容，服务应按什么顺序更新？ | 多个服务共用一张表时，单服务验证不足以证明可以改表 |
| 后台任务和队列 | 旧 worker 是否排空，定时任务是否重复运行，旧消息能否被新消费者处理？ | 防止重复消费、重复扣款、漏任务和延迟爆发 |
| 缓存、搜索与静态资源 | 缓存格式是否兼容，是否需要重建索引，CDN/旧浏览器是否仍引用旧资源？ | 避免上线成功但用户仍拿到旧页面，或清空缓存导致数据库流量突增 |
| 网络与访问 | 端口、DNS、证书、代理路由、负载均衡和健康探针是否匹配？ | 填写域名不会自动完成路由；切流前要确认新实例能够实际提供服务 |
| 主机与容量 | CPU、内存、磁盘/inode、镜像下载、索引构建和新旧实例并存是否有空间？ | 蓝绿发布、备份和大表迁移会临时提高资源需求 |
| 安全与权限 | 镜像漏洞、来源、服务账号权限、端口暴露、特权容器和挂载是否变化？ | 发布引入的新增权限与暴露面应明确可见；核查缺失不能显示“安全” |
| 流量与停机 | 是否支持并行实例、何时排空旧连接、是否需要停写、允许多长不可用？ | 普通 Compose 重建本身不保证零停机；没有双实例和代理能力时应明确维护窗口 |
| 验证与观察 | 容器就绪、关键 API/业务用例、错误率、延迟、队列积压和数据库负载是否达标？ | “容器运行”与“用户业务正常”要分别显示；探针应采用无损或受控测试数据 |
| 恢复与外部副作用 | 哪个版本可回退，是否需要向前修复，备份是否可恢复，支付/通知/文件写入如何处理？ | 已发送通知、外部扣款和用户新数据不能靠回退代码撤销 |
| 协作与状态漂移 | 是否有另一客户端、CI 或人工操作同时修改目标；批准后配置是否改变？ | 防止按旧预览执行新配置，或两个发布同时迁移同一个库 |

不是每次都执行所有项目：不涉及的项目需要有可追溯依据；证据不足应显示“未核对”。例如，没有填写迁移信息不能自动推断本次不涉及数据库。

还要检查容器 entrypoint/启动脚本是否会自动运行 migration、seed 或权限初始化，避免这些副作用躲在“启动容器”后面。迁移最好由一个明确、受控的任务执行，而不是每个应用副本启动时竞争执行。

## 5. 发布计划与执行顺序

### 5.1 一份版本要固定哪些信息

- 源码提交、完整服务到镜像 digest 的映射、构建来源与目标平台。
- 可恢复的非敏感配置版本、秘密引用和功能开关变更。
- 迁移文件标识、顺序、checksum、执行工具及版本、执行环境、目标数据库身份。
- 必须先完成的依赖、数据回填任务、约束校验及当前迁移历史。
- 新旧应用的读写兼容条件、允许的回退版本与回退窗口。
- 切流方式、维护窗口、验证用例、观察阈值、停止条件和故障处理分支。
- 与风险匹配的备份/恢复证据，包括恢复点、可接受数据损失和预计恢复时间。

迁移脚本与应用产物必须属于同一已冻结的发布计划。Agent 修改脚本、用户换版本或目标配置改变后，之前的检查和确认均需失效。

### 5.2 常见的兼容性发布路径

```mermaid
flowchart LR
    A[识别变更与目标] --> B[预检及恢复条件]
    B --> C[确认固定计划]
    C --> D[兼容性迁移]
    D --> E[部署兼容应用]
    E --> F[按依赖执行回填与校验]
    F --> G[切换流量或功能开关]
    G --> H[业务验证与观察]
```

这不是所有发布都固定照搬的流水线。若新应用必须依赖已完成的历史数据，回填必须成为启用该功能的前置条件；若支持兼容回读，可在兼容应用上线后独立执行。破坏性清理应推迟到回退窗口结束，并成为单独的发布计划。

备份不要求每次都做一次昂贵的全量复制。应根据风险核验现有备份链/快照/PITR 是否覆盖本次恢复需要，以及是否有近期恢复演练证据；不能用“备份任务成功”替代“可恢复”。需要恢复数据时，先明确停写、恢复点、备份后的新数据和外部副作用如何处置。

### 5.3 执行与持久记录

每个阶段分别记录“未开始、运行中、成功、明确失败、结果未知”，保留执行证据、起止时间和恢复条件。一个阶段失败时不能把之前已执行的步骤抹掉。

- 迁移优先调用项目既有框架的正式执行入口，不把一整套工具拆成任意 SQL 或 Shell 重新实现。
- 记录迁移 checksum 和已应用历史；发现历史脚本被改动时停止，不通过自动修改历史来消除错误。
- 发布锁与数据库迁移锁分别覆盖真实目标。多个 Compose 项目共享数据库时，仅锁项目不能防止并发改库。
- 重试和续跑必须由对应迁移工具、任务记录及预检共同证明可行；不承诺分布式场景下“绝对只执行一次”。
- 断连/超时后先核查执行器、数据库迁移历史、锁和实际结构。仅看到字段存在不能证明迁移全部成功，也不能证明旧任务已停止。
- 迁移已成功而应用失败时，若旧应用兼容新结构，可回退应用并保留扩展结构；否则停止切流或停止继续操作，选择已准备的向前修复/恢复流程。
- 部分数据回填不能通过重新从头执行来碰运气；需要可核对的游标、幂等条件、影响上限和验证。

现有普通 Agent 的数据库权限不能因新增发布模块而自动扩大。若项目迁移工具需要超出通用 SQL 写工具的能力，应设计独立、用户批准、精确绑定目标的迁移执行合同；不能用 SSH 绕过现有禁用表或写入限制。

## 6. 页面怎样表达，避免再次堆满卡片

沿用现在的单一发布工作区，把左侧“本次变更”升级为可展开的发布影响列表，只突出本次涉及的部分：

| 影响项 | 摘要示例 | 展开后展示 |
| --- | --- | --- |
| 应用 | 2 个服务更新 | 镜像差异、构建、依赖顺序 |
| 数据库 | 新增 1 字段、创建 1 索引 | 目标库/schema、迁移文件、真实起点、脚本 diff、依赖、锁与资源风险、当前执行状态 |
| 数据处理 | 回填 display_name，规模待核实 | 预检依据、批次、限速、进度、恢复游标和校验 |
| 配置/网络 | 新增 1 个配置项；路由无变更 | 非敏感差异、秘密引用、目标路由 |
| 恢复方案 | 应用可退到兼容版本 A；数据库保留新增列 | 可回退证据、失效条件、备份/向前修复入口 |

右侧保留检查结论，但结论应来自真实证据，显示“通过 / 提醒 / 阻断 / 未核对”以及观察时间。回退能力分为“可回退”“有条件回退”“仅支持向前修复”“待核对”，不默认给所有历史版本一个可执行回退按钮。

确认面板明确呈现目标数据库、将执行的迁移、影响范围、是否可能锁表/停写、数据保留与恢复限制。迁移脚本和完整计划可展开审阅；低风险步骤可以合并在一次已冻结计划的确认里。数据破坏、数据恢复或计划外变化需要独立确认。

运行详情按阶段展开，不只展示单条“发布中”进度条。例如“迁移完成、应用验证失败”应保留两种事实，并给出适用的恢复入口。部署历史记录整次发布和各阶段结果，继续复用程序现有审计，不另做审计工作台。

## 7. Agent 与模块怎样协作

| 时点 | Agent 的作用 | 模块承担的职责 |
| --- | --- | --- |
| 准备阶段 | 读取已授权代码、migration、模型、接口及依赖；识别遗漏；生成可审查迁移或计划草稿 | 校验来源、目标身份、权限和版本，保留待确认候选 |
| 发布前 | 根据真实结构、统计和报告解释风险，指出旧版本是否还能读写 | 检查基线漂移、产物可用性、checksum、兼容证据、备份、锁及资源预算 |
| 执行中 | 解释已观测到的结果，协助定位失败步骤 | 执行已批准计划、持久化阶段状态、控制并发、停止后续动作 |
| 发布后 | 对比指标和业务验证，生成发布摘要或恢复建议 | 根据实际验证决定成功/失败/未知，保留历史，校验恢复条件 |

Agent 不能自行把“看起来安全”变成检查通过，也不能因测试用例没报错就承诺业务兼容。缺少代码、结构、运行结果或数据库规模依据时，应把缺口交给用户，而不是补一个估算数字。

## 8. 关联模块与性能影响

关联边界：发布模块需要关联既有服务器、Docker、数据源、远程文件、独立任务、权限和审计；可选关联 CI、代理、监控、缓存及队列。应通过明确的能力接口接入，保留原来的连接身份、逐次确认和表级限制。应用回退不隐式改动数据库账号、容器引擎版本或数据卷。

性能主要来自数据库工作和实际部署，而非页面：

- 预检先读迁移历史、系统目录与统计，按需读取精确目标；不在每次页面刷新时全库扫描或做全量 COUNT。
- 大表变更先在有代表性的隔离环境演练；生产前根据真实版本、表规模与负载重核对，预计耗时标明依据和不确定性。
- 回填分批限速，设置锁等待、批次耗时、复制延迟、错误率和延迟阈值，超过预算暂停。
- 评估镜像拉取、新旧实例共存、索引临时文件和备份空间的峰值，避免只检查稳定运行时的用量。
- 重任务在受控远端执行；桌面只接收有界状态与输出。页面关闭不等于任务停止，桌面重启后不自动重放。

## 9. 推荐落地顺序与验收场景

先做**能够说明影响和恢复条件的发布计划**，再逐步开放执行能力：

1. 先支持无数据库变更与向后兼容的增量迁移，接入项目已有迁移框架；具备迁移目标绑定、冻结脚本、执行记录、互斥和应用回退校验。
2. 增加分批数据回填、约束校验、分阶段字段替换和共享库的依赖检查。
3. 按真实环境能力增加蓝绿/灰度、流量控制和观察阈值。没有这些条件时如实提示维护窗口。
4. 删除字段、破坏性数据转换、数据库引擎升级和数据恢复采用独立维护流程；支持计划与可审查执行，不能伪装为通用一键回退。

首批验收至少包含：无迁移发布；新增可空字段后应用失败并可退回兼容版本；NOT NULL 遇到旧数据；大表锁等待超时；已执行脚本 checksum 变化；数据库基线漂移；同库不同项目并发迁移；迁移执行后断连；迁移成功但结果落盘失败；回填部分完成后恢复；旧消费者处理新消息；备份不可恢复或密钥已撤销；旧应用不能理解新业务状态。
