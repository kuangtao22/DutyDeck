# 项目知识库场景灵活性评审

日期：2026-10-08

评审对象：[按主题提炼的简化方案](2026-10-07-project-knowledge-simplified-extraction.md)，本次读取的 140 行版本。仅评审设计及必要的现有实现边界，未修改设计正文或应用代码。

后续修订（2026-10-08）：用户随后指定“扫描分析 → 用户确认分组清单 → 生成大纲 → 补全文件”的两步流程，设计正文已结合下述建议更新。本文保留当时的评审依据与行号；新文本尚不代表功能实施完成，原评审结论也不作为新文本已独立复核的证明。

结论：**需修订后实施（REQUEST CHANGES）**。方案已经取消固定目录模板，允许用户定制、项目记忆统一和按需检索；但这不等于全链路已保证场景开放性。独立规范评审为 REQUEST CHANGES，独立架构评审为 WATCH。发现 1 项 P1、4 项 P2，均可在现有架构内补强，无需另建模板引擎或通用知识平台。

## 1. P1：未明确解除旧提交链路中的封闭业务分类

**依据：** 设计第 31、61 行要求目录动态编排、不能按关键词硬编码；第 89、95 行的接入说明尚未包含旧业务分类迁移。现有实现仍包含：

- `packages/shared/src/types/project-knowledge.ts:2` 的七类 `KnowledgeCategory`。
- `apps/electron/src/main/lib/project-knowledge-tools.ts:44` 的封闭 category，以及提交候选必填分类。
- `apps/electron/src/renderer/components/agent-skills/ProjectKnowledgeTab.tsx:52` 的固定分类选项。
- `apps/electron/src/main/lib/project-knowledge/scanner.ts:224`、`organizer.ts:37` 的关键词归类。

**触发与影响：** 用户要求“客户 / 活动 / 交付物”或完全不同的组织方式。如果只增加文件树而继续沿用旧提交与整理合同，业务内容仍需映射到旧七类，Agent 生成的组织方式可能在展示、提交或后续整理中被限制。这里指出的是设计遗漏的迁移边界；动态目录尚未实施，不能将旧实现误称为新方案的运行结果。

**最小修订：** 明确项目类型只作理解线索，不作为封闭枚举或能力开关。以稳定文档身份与真实目录组织知识；旧业务分类退出必填校验和关键词重分类，必要的历史标签可保留为兼容元数据。共享类型、工具/IPC 校验、持久化与迁移、UI/检索及整理器同步适配。来源类型、操作状态等运行时枚举仍可保留，它们不应决定业务目录。

## 2. P2：正文与合并规则偏向单一结论，缺少多对象、多方案边界

**依据：** 第 73 行要求正文写“结论、适用范围、必要理由”，第 77 行只列稳定需求、决定、规则和偏好；第 91 行定义唯一 `topicKey` 和当前正文，第 124 行要求同主题材料形成一篇说明。尚未明确“同主题”与“同一个知识对象”的区别。

**触发与影响：** 同一项目同时服务两位客户、两个活动阶段，或者研究与创作保留 A/B 方案。若只按主题合并，客户偏好或阶段约束可能混在一起；未决方案可能被当成冲突或旧版本收起。访谈、研究假设、时间线、操作步骤也不适合强制改写成同一种结论文体。

**最小修订：** “唯一正文”适用于同一个知识对象，不等于每个大主题只能有一篇文档。按可独立引用的对象/议题建立身份，合并前比较适用对象、范围和阶段；需要独立检索的并行方案可拥有各自正文，以主题链接关联。正文结构按内容与用户要求选择，简短摘要保留在索引中，无需每篇强制相同章节。对未来任务有价值的假设、备选、反证和阶段结果可以保留，标明适用范围及确认状态；不得自动升格为事实，也不要求穷尽保存所有聊天。

## 3. P2：目录稳定与自动整理的边界不一致

**依据：** 第 59 行以用户明确要求描述合并/拆分，第 74 行又允许主题增长后整理；第 131 行“没有新主题时不新增目录”可能阻止同主题下按新对象或阶段合理拆分。

**触发与影响：** 主题增长时，实现可能完全停止自动整理，或反过来自动改变用户指定结构。这分别损害自动维护能力和用户定制的可预测性。

**最小修订：** 延续用户已经提出的自动优化要求：Agent 生成且未被用户明确固定的结构，可以按语义增长自动整理；用户指定的目录、命名和归档规则优先。只有存在实质歧义、需偏离用户约束或会丢失独立内容的合并才提出方案，不把每次移动都变成人工审批。移动和改名保持身份；拆分新增子文档身份，合并记录原身份指向，并可撤销。每次整理同步更新索引与内部链接，保留旧路径的可定位入口。“稳定”指内容身份和可达性，不要求物理路径永不变化。

## 4. P2：增量规则没有明确覆盖首次未审阅的材料

**依据：** 第 71 行先读取少量代表正文，第 77 行允许分批并保留进度，但第 84、117 行将后续范围描述为变化来源和受影响主题，未明确未审来源如何继续处理。

**触发与影响：** 一份重要材料首次未被抽中，之后也没有修改。若实现按“仅变化”调度，它会长期遗漏；无 README、主要信息位于普通文档或代码中的项目更容易漏掉关键内容。

**最小修订：** 复用已有来源进度和处理水位，明确更新范围为“新增、变化、尚未审阅且属于本次范围”的材料；按需选择、按预算继续，并显示剩余范围。目录识别和提炼步骤可以按当前任务局部执行，不能强制每次重新跑完整规划。默认忽略的业务噪声可按用户任务纳入，权限、内部生成物和来源校验边界继续保留；无需每轮全量扫描或新增一套调度系统。

## 5. P2：完全空项目的初始化行为未定义

**依据：** 第 71、123 行要求首次得到概览与目录，第 31、61 行又禁止凑空目录和悬空文档；第 130 行只覆盖“有用户指令、没有原材料”。

**触发与影响：** 空目录没有材料、记忆或明确项目目标，只点击“更新知识库”。实现可能套用默认模板、虚构概览，或没有可理解的结果。

**最小修订：** 默认仅记录已知项目身份、索引和缺口，不推测行业或制造空主题；获得首个有效输入后逐步建立知识。用户明确要求目录骨架时，可以创建真实目录并标记待补，不能将空目录视为已提炼成果。模板可作为用户主动选用或 Agent 提议的起点，始终可以改写、混用或弃用，不成为创建项目的必选步骤。

## 保留的约束与能力边界

- 真实文件、独立正文、来源可追溯、并发版本校验和可恢复整理是数据正确性要求，不限制行业或项目类型。
- 项目记忆归属、跨项目访问范围和执行权限保持现有边界；知识归档不自动授予执行权限。
- 接口工作台拥有接口定义及文档，Canvas 拥有创作源；二者是可选业务能力，不是建立知识库的前置条件。接口文档不在知识库另建副本。
- 解析能力应明确说明。当前扫描器对 PDF/Office 等只登记元数据，不能把目录可容纳这些资料等同于已理解正文；这是当前能力限制，不应包装为场景限制或完成承诺。
- 不需要增加每行业一套代码分支或复杂自定义字段平台。首先开放目录、内容组织和适用范围，复用现有存储、版本和检索。

## 补充验收建议

| 场景 | 应证明的行为 |
| --- | --- |
| 用户给出旧七类之外的目录 | 创建、提交、重启、搜索与增量维护均保留自定义组织，不被关键词重分类 |
| 同一项目混合调研、活动与软件交付 | 不要求选择唯一项目类型，各主题按实际材料组织 |
| 两个客户及未决 A/B 方案同时存在 | 可独立查阅与检索，适用范围清楚，不误合并、不把候选当已确认结论 |
| 用户指定正文为时间线或操作步骤 | 保持合适文体，不强制相同章节；索引仍有简洁摘要 |
| 内容增长且无新大主题 | 可自动合理拆分；用户固定结构不漂移，旧链接可定位并支持撤销 |
| 首次预算不足，剩余材料没有修改 | 后续仍可补读未审部分；未处理完不报告全项目已完成 |
| 零材料，随后补充一句项目目标 | 初次不套模板或编造事实，新增输入后逐步生成真实知识 |

开销影响：开放业务分类本身无需增加模型调用；多对象分开索引可减少错误召回，未审来源仍沿用分批预算，目录调整只刷新相关路径和链接。无需全量上下文或按场景启动额外 Agent。
