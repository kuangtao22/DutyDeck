# 编排工厂：当前会话 Agent 完整代操作

日期：2026-10-09
状态：用户已于 2026-10-09 确认；实现已接入，最终验证记录见对应计划。

## 目标与用户体验

用户在工厂旁的现有 Agent 会话中表达目标，Agent 即可完成场景管理、用例准备、运行、批量测试、读取评审建议、修改候选、对比、采纳和本地交付。右侧工厂显示同一份真实进度与记录，用户仍可随时检查和手动操作。

典型请求：“用已保存的这 10 条任务批量测试，根据评审建议最多优化 3 轮，把改善和退化列出来。”Agent 自动完成测试与候选验证，准备好结果后直接发起采纳审核弹窗，无需用户再去右侧寻找按钮或先做一轮文字确认。**采纳始终由用户在弹窗明确确认，完全自动执行模式也不能跳过。**删除、丢弃和回滚等破坏性动作仍逐次确认。

这是对旧“Agent 提案、人工必须在工厂点击采纳”产品约定的调整。不能继续用旧提示词、默认 Skill 或工具白名单把代操作功能永久禁用。

## 实施前核实的现状

- Agent 当前有 13 个工厂工具：读取场景/版本/桩/任务/运行记录，准备和写入草案/桩，单步试跑与单条整链对比。
- UI 与服务层已经支持数据集管理、批量评测、场景管理、采纳、回滚和导出，但没有向 Agent 完整暴露。
- 多任务优化对比逻辑在 renderer；批次完成状态只存在页面内存，Agent 的对比记录无法直接构成同等的已验证批次。
- Agent 步骤参数允许宽松对象，准备和保存草案未执行完整结构校验；未知字段可能直到运行才被拒绝。这与截图中的 `steps[0]` 含 `name`、`outputSchema` 的错误相符，但本轮未读取截图对应的真实业务数据。
- Agent 工厂运行只有 runner 自身超时，没有贯通当前 Agent 回合的主动取消；批量执行前需要补齐。

## 方案比较与选择

| 方案 | 用户影响 | 判断 |
| --- | --- | --- |
| 完整代操作，UI 与 Agent 共用业务服务和批次证据 | 一次委托可完成整个流程；涉及生效的操作有准确版本与结果可查 | 推荐，符合“所有功能可代操作” |
| 只补数据集和批量评测工具 | 能批测，但采纳、交付和完整对比仍需手工接续 | 可作为开发顺序中的第一段，不作为最终范围 |
| Agent 模拟点击工厂按钮 | 依赖面板位置、弹窗与焦点，长任务结果难可靠恢复 | 不采用 |

## 能力范围与操作边界

| 工厂能力 | Agent 可执行的操作 | 必须保留的约束 |
| --- | --- | --- |
| 场景管理 | 新建、读取、重命名、修改步骤/契约/模型/评审、删除 | 精确场景身份；删除前展示影响并确认 |
| 草案与版本 | 保存、丢弃、查看差异、采纳、读取历史、回滚 | 版本与草案内容校验；不能覆盖用户同时编辑的新内容 |
| 测试资料 | 读取保存任务，创建数据集，批量添加/删除用例，管理桩 | 用例来源可追溯；真实输入与合成用例分清；占位桩不能作为质量通过证据 |
| 执行 | 单步、整链、批量测试、读取原始输出与逐步评审 | 真实进度、可取消、范围有上限；计划模式不能发起模型调用或写入 |
| 优化 | 汇总问题、修改候选、同条件批量对比、读取修复/退化/未知项 | 固定输入、标准和实际模型；不得通过放宽标准制造改善 |
| 交付 | 查看交付记录、生成本地能力包、定位导出文件 | 沿用交付校验；本地导出不等于发布或写入消费项目 |

“可代操作”意味着 Agent 有受控工具入口，不意味着每个请求都自动包含全部后续动作。用户只要求测试时，Agent 不擅自采纳或删除；用户明确委托完整流程时，候选、数据集、评审标准准备和测试可连续执行，采纳必须逐次审核。审批由宿主和真实用户交互提供，不能接受模型自报的 `approved=true`，也不允许“总是允许”跳过未来采纳。

按用户实测纠正，采纳复用 Agent 原有权限审批卡，不使用独立全屏模态。卡片展示宿主计算的实际改动前后；Agent 可以随采纳提议说明具体问题、预期收益和取舍，明确标为待验证判断，不能混入宿主的测试结论。无匹配批次时仍展示草案差异与修改说明，只在验证状态解释一次未验证。匹配批次的实际收益、当前问题与覆盖范围仍从持久运行证据生成。不增加模型调用；当前版本、草案或测试证据变化后旧批准失效。用户拒绝保留草案与结果，失败保留卡片可重试，通用 Enter 不能误批。

## 批量测试与优化闭环

1. 读取当前场景、草案、保存任务和数据集，先检查定义结构、输入、评审标准及模型可用性。缺少条件时返回字段位置和修复建议，不反复发起必败测试。
2. 建立可追溯批次，冻结场景版本、草案完整内容、输入集及其版本、评审标准与模型绑定。逐条运行并自动评审，保留每条运行 ID。
3. 当前会话 Agent 读取汇总，再按需读取失败用例的完整输出、步骤评审、证据和建议。区分执行失败、输出约束失败、内容未达标和评审自身失败。
4. 根据已授权的优化目标保存候选。提示词优化只改模型步骤提示词；流程、契约、评审或模型变更走独立的场景修改与重新验证，不能沿用原评分。
5. 用相同冻结输入、标准和实际模型比较当前版与候选，按整批统计改善、退化和未知项。批次证据由主进程保存，UI 和 Agent 使用同一套比较规则。
6. 达到目标、无改善、预算耗尽、用户停止或版本冲突时结束；返回最好已验证候选、剩余问题与执行成本。只测试一个样本时明确证据范围，不宣称泛化改善。
7. “通过后采纳”要求候选在整批中通过、无退化与未知项，并有可核对改善。执行时再次验证版本和草案身份；用户明确要求普通采纳时沿用普通采纳语义，不把它标成“优化已验证”。

已实现每批最多 10 条用例、每个 Agent 回合最多 3 轮优化，默认串行；整链、单步和批次共用每回合 60 次运行单元上限，由宿主限制。数据集容量不受单批上限限制，超过 10 条时使用 caseIds 分批选择；UI 默认勾选前 10 条。人工显式启动的批次不累计成会话永久三轮限制。每条任务可能包含多步模型执行、逐步评审及重试，一轮双版本对比的成本明显高于单次运行，不能将“10 条用例”误报成“10 次模型调用”。额度达到后保存结果并停止，不自动扩容。

## 实现边界与关联影响

- 在现有 `CapabilityFactoryService`、runner、evaluator 和 Agent facade 上扩展明确的白名单操作；不开放任意 IPC 分派或磁盘路径，不新增一套 Agent/runtime。
- 将 renderer 中适合共用的比较计算移到共享纯逻辑，将批次执行和证据保存放在主进程；现有 UI 也接入同一入口。旧运行记录继续可读，缺少批次证明时不得补造证明。
- 增加定义预检：拒绝未知字段并返回准确路径；允许编辑中的草案保留明确的未就绪状态，运行和采纳时执行对应门槛。不擅自把未知字段删除或猜成其它字段。
- 准备、批准、应用之间保存不可变快照，执行时校验当前版本与待处理草案，防止旧批准覆盖新状态。
- 贯通 Agent 停止、单次模型超时和批次停止信号。逐条保存完成结果，取消后停止后续请求；会话归属或工作区失效时禁止越界写入，不能为了补终态绕过写守卫。
- 操作和进度按会话、工作区、场景、批次隔离，通过事件更新右侧；不抢走用户正在阅读的记录，不覆盖编辑器未保存内容。
- 不因为工厂拥有新工具而扩张 Automation、Collaboration 或受限运维模式的能力；这些来源的准入和停止行为需要单独回归。
- 更新产品内 Agent 提示词、默认 `capability-factory-scene-design` Skill、工具说明与相关测试，使“可代操作”口径一致；修改默认 Skill 时递增版本。README、tutorial 与发布日志在另有授权时更新。

存储仍使用现有 JSON/JSONL 与安全原子写，不新增依赖或数据库。默认串行避免无控制的模型并发；列表只返回摘要，完整输入输出和证据按 ID 获取，降低主进程读取、工具结果体积和 Agent 上下文消耗。

## 开发顺序与验收

按同一目标分段落地：先补定义预检、取消与会话隔离，再开放完整操作面，然后统一并持久化批量测试/优化对比，最后更新右侧进度和内置引导。不能只新增工具名却遗漏宿主接线、权限策略或结果展示。

BDD 验收覆盖：完整委托闭环；批量用例正常及失败；评审失败与未知不得算通过；标准/模型不同的对比拒绝；草案或数据集并发变化；停止后不再发起下一次调用；工作区迁移或会话失效；拒绝或过期审批；重开面板可读取同一批次证据；旧数据兼容；受限模式不扩权。运行相关定向测试、Bun 类型检查和必要的 Electron 集成验证。

本轮交付包含代码、离线模型端口集成测试和隔离 Electron UI 冒烟；未调用真实模型、修改用户工厂业务数据、提交或发布代码。
