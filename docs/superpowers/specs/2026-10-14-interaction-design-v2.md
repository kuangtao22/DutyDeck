# 交互设计 V2：以体验和对话为中心

日期：2026-10-14。状态：可点击评审稿的设计说明，非已接入 DutyDeck 的产品功能。

[打开 V2](../../prototypes/interaction-design-v2/index.html) · [打开 V1](../../prototypes/interaction-design/index.html) · [完整业务定义](2026-10-14-interaction-design-module.md)

## 结论

建议用 V2 作为日常入口：主会话与一个可直接操作的产品预览并列，默认让用户体验产品。需要改动时进入「选择修改」，选中元素后才出现编辑卡；页面总览、交互流程和版本记录按需打开。V1 保留供对比，它更适合集中审视多页面的布局与视觉一致性。

业务目标不变：把需求变成可演示、可迭代、可交接的原型。改变的是操作顺序：用户先发现流程或表达上的问题，再定位并修改，而不是先学习画板和属性面板。

## 为什么调整

用户通常从「我想做什么」「这个地方不好用」开始，并不天然知道要改哪个页面或组件。V1 同时展示页面列表、画板、属性与会话入口，空间分配偏向设计工具；用户必须先理解编辑器，才能试用产品。

V2 把高频任务收敛成一条短路径：

1. 在主会话说明需求，查看生成结果及边界。
2. 直接点击预览，体验任务路径。
3. 发现问题后切到「选择修改」，选中标题、说明或主要操作。
4. 手动改文字，或带着页面、元素和版本引用向 Agent 提要求。
5. 在主会话比较候选，预览后采纳，再继续体验。

这能减少来回切换，也让讨论、变更范围和采纳结果处于同一上下文。它仍然需要明确的体验/选择模式：同一个按钮的点击不能同时代表「执行打卡」和「选中按钮」。

## V1 与 V2 的取舍

| 任务 | V1：画板优先 | V2：体验优先 |
| --- | --- | --- |
| 打开后做什么 | 浏览多页面，再进入演示 | 直接操作当前页面 |
| 与 Agent 沟通 | 在画板与会话之间切换 | 主会话常驻，候选就在讨论旁 |
| 小范围修改 | 常驻属性面板 | 选中时出现简洁编辑卡 |
| 比较视觉一致性 | 多页面并排更直接 | 需要打开总览；详细横向比较较弱 |
| 检查业务流程 | 进入演示与流程视图 | 日常预览即可体验，流程视图辅助定位 |
| 窄工作区 | 多栏需要折叠 | 预览与会话互斥切换，避免挤成窄栏 |
| 适合对象 | 设计师集中排版、批量审视 | 产品负责人、独立开发者、评审者持续迭代 |

另外考虑过「纯聊天、只提供结果链接」：界面最简单，但每次查看都脱离上下文，元素定位也不清晰，因此不作为推荐方案。V2 保留实时预览和主动选择，避免所有精确操作都依赖自然语言描述。

## 界面与行为合同

主工作区只运行一个活动页面。底部步骤条用于快速定位四个示例页面，不把直接定位计为完成用户流程；实际完成任务应通过页面内按钮触发。

「体验」执行页面动作；「选择修改」拦截页面业务动作，只选择已登记字段。编辑卡显示范围、文字与主要操作的去向，主会话同时出现对应引用。取消选择、切页或回到体验后清理无效引用。没有明确选择时，会话上下文是整个原型；评审稿的预设候选须显式说明实际修改对象。

Agent 候选展示修改前后及基线版本，预览不写回当前稿。本评审稿的候选预览仅用于比较外观，采纳后再体验交互。手动修改、撤销和历史恢复都形成新的当前版本，旧候选只能参考，不能覆盖新内容。取消操作使在途结果失效。

正常、空、加载和错误是临时体验场景，不等于修改产品设计。重置体验清除打卡和场景状态，不撤销文案、配色或连接修改。静态连接检查与实际点击记录分开展示；修改后不把旧体验记录当成当前版本的验证证据。

辅助弹窗提供总览、流程与历史，并支持关闭后回到发起位置。窄屏仍需保留历史、撤销、导出和模式切换入口，不能因侧栏折叠而丢失功能。

## 本轮评审稿与目标能力

本轮沿用「拾光」习惯 App 四页，目的是让 V1/V2 用同一产品比较工作方式。独立目录和缓存隔离，V2 不改写 V1。

| 能力 | 本轮评审范围 | 正式模块目标 |
| --- | --- | --- |
| 产品体验 | 四页路径、打卡反馈、临时状态与恢复 | 用户生成的多页面原型及明确业务规则 |
| 局部编辑 | 登记的标题、说明和主要操作文字 | 稳定元素身份下受控字段编辑 |
| Agent 修改 | 文案与配色两类明确标记的预设候选 | 模型依据需求、引用和锁定项生成候选 |
| 候选管理 | 比较、外观预览、采纳、取消、过时阻断 | 绑定运行、原型与版本的完整候选流程 |
| 流程检查 | 登记连接的静态检查及点击进度记录 | 可执行场景及绑定版本的测试证据 |
| 历史与缓存 | 独立浏览器本地缓存和有限版本记录 | 项目文件持久化与可追溯版本 |
| 交付 | 当前内容导出为独立 HTML | 固定版本的资源、行为说明和验证记录 |

本轮不支持任意需求生成新页面，不接真实 Agent、后端、账号或 DutyDeck 业务数据。未识别的请求应明确说明模拟范围，不能返回虚假的成功结果。手机/桌面切换展示不同布局，不代表已生成原生 App。

Agent 最值得承担的是需求拆解、结构草拟、受控局部修改、补齐状态及交接整理；用户保留设计取舍与采纳权。任意 HTML 的完整双向可视化编辑、真实接口联调及生产上线不由此原型承诺。

## 关联模块与资源影响

本轮仅新增独立评审稿，不修改 Canvas、主会话、项目持久化或 Agent runtime。正式集成时应复用 DutyDeck 主会话、HTML 沙箱与版本服务，但原型身份和 Flow 需要独立约束，不能把页面跳转塞进 Canvas 素材生产关系。

正式编辑仍采用 Jotai、既有主题和 Radix/shadcn primitives。新增接口需同步检查 shared、main、preload、renderer 四层；持久化沿用本地 JSON/JSONL 和原子写入。预览继续限制外部网络及文件访问，不能为页面跳转放开宿主权限。

V2 只运行一个页面，总览用静态缩略内容，降低多页面同时运行的资源开销。候选尽量记录局部变更，避免每次复制大资源；正式历史需要明确保留策略与资源去重。当前独立稿的小型快照不代表大型工程已完成性能验证。没有新增运行时依赖或产品常驻服务。

## 对比体验与验收

建议依次体验：完成一次打卡 → 选择按钮修改文案 → 请求预设候选并比较 → 生成期间手动编辑以观察过时保护 → 调整连接并检查 → 恢复历史 → 导出独立 HTML。

评审重点是能否清楚回答「现在是在用产品还是改产品」「Agent 准备改哪里」「哪个版本已生效」「哪些检查真的执行过」。若这些判断仍需要解释，应优先改交互反馈，而不是继续堆积工具入口。

本轮实际 Chrome 验证共 59 项通过，无页面脚本错误，包含完整打卡、局部修改、候选比较/采纳、生成期间冲突与取消、历史恢复、离线 HTML 导出、键盘选择和 390/605/820px 窄窗。截图验收修正了桌面提示覆盖底部导航的问题；文件哈希确认 V1 内容没有改变。真实模型质量与 Electron 集成不在本轮验证范围内。
