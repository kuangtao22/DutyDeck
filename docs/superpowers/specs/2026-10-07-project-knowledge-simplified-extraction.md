# 项目知识库：按主题提炼的简化方案

日期：2026-10-07

修订：2026-10-08，用户要求采用两步建立流程：先扫描分析，提交分组信息清单供用户确认；确认后按清单生成知识库大纲，再逐项补全内容文件。用户进一步确认采用类似 Obsidian 的普通文件夹、Markdown、附件及相对链接存储，支持外部阅读与编辑。目录与内容组织保持开放，项目记忆纳入同一知识库，接口文档由接口工作台自动呈现。

状态：根据真实使用反馈提出的修订方案；此前已修复显示和内部文件噪声问题。本次仅更新设计，两步建立流程、动态目录、可外部编辑的文件存储、记忆统一和接口文档视图尚未实施。以下产品方向替代此前以大量来源条目、固定分类和碎片候选为中心的设计，并纳入场景灵活性评审的修订建议。

## 要解决的问题

用户需要打开项目就能知道“项目做什么、怎么做、哪些决定已确定”，并让下次对话直接续接。知识库的主要成果应是有结构、可阅读、持续更新的项目说明。

知识库拥有自己的真实文件与目录。原项目文档、用户指令和对话是输入材料；Agent 读取、提炼、合并和改写后，在知识库目录创建独立、完整的文档。用户浏览、编辑和新会话检索的都是这些自有文档，不能用原文链接、虚拟分类或哈希条目列表替代。原文只作为可展开的来源依据。

本轮只读核对 TaokoPlay：清单有 1,383 个来源和 6 条提炼知识，6 条正文均已保存；来源大部分是图片、代码和脚本。已有知识混合了业务规则、实现细节、版本状态与操作限制，缺少项目总览及主题层次。界面还暴露了长来源 ID、重复引文、扫描统计、整理操作和旧记忆维护入口。

独立错误另行修复：同一来源多个引文导致 React key 重复；快照计数与目录刷新之间错误显示空库；知识库自身的锁和版本文件混入 Agent 的代码改动列表。截图中的 68 项改动不能解释为 Agent 修改了 68 个业务文件。

## 方案选择

| 方式 | 结果 | 判断 |
| --- | --- | --- |
| 继续增加零散知识卡片，再补分类和过滤 | 短期改动少，但数量越来越多，同一主题容易散落多处 | 不作为主要阅读方式 |
| 项目概览 + 持续更新的主题文档 | 一眼看清项目，细节可按主题展开，适合用户和新会话共用 | 推荐 |
| 直接维护一份超长 MEMORY.md | 开始简单，增长后加载成本高，容易重复和冲突 | 只保留紧凑索引，不承载全库 |

## 用户看到什么

首次建立时先呈现 Agent 分析得到的分组信息清单，支持用户修改并确认。确认后展示可阅读的大纲、各项补全进度，以及已经保存的目录与正文；日常使用以文件树、正文、搜索和“更新知识库”为主。文件夹和 Markdown 文件实际落盘，支持整体备份和导出；来源、历史和撤销在具体文档详情中按需展开。

分组由当前 Agent 理解项目目标、现有材料和用户指令后提出，用户确认后再编排对应目录、文档大纲与导航索引。项目类型只作辅助理解，不是封闭枚举或功能开关，混合场景无需选择唯一类型。用户可直接要求“按策划阶段组织”或“改成客户、活动、交付物三层”；不预设软件项目分类，不限定目录数量，模板只能作为可调整的起点。默认不为填满模板创建空文件夹，用户明确要求目录骨架时可创建并标明待补。

以下仅为活动策划项目的一种可能结果，不是默认模板；研发、市场调研、内容创作等项目应产生适合自己的结构：

```text
项目知识库/
├── 索引.md
├── 项目说明.md
├── 策划目标/
│   ├── 目标与受众.md
│   └── 成功标准.md
├── 调研与洞察/
│   └── 用户需求.md
├── 活动方案/
│   ├── 创意与流程.md
│   └── 渠道与传播.md
├── 执行与交付/
│   ├── 排期与分工.md
│   └── 预算与资源.md
├── 合作约定/
│   ├── 已确认决定.md
│   └── 客户偏好.md
└── 设计素材/
    └── 已采用海报.png
```

“搬运”默认指整理内容并写入新目录，原文件保留。适合原样保存的正式稿件和图片可复制选定资产到库内，并从知识文档以相对路径引用；不搬走整个原项目目录。用户直接给出的规则、规划或决定也可在没有原文档时生成对应知识文件。

用户确认的清单确定整理范围和分组意图。范围内再次扫描优先更新已有文档；Agent 生成且未被用户固定的子结构，可以随对象、阶段和材料增长自动拆分或整理，不能因措辞变化反复搬动文件。用户指定或手工调整的组织方式优先；新增超出已确认范围的分组、偏离用户约束或有损合并时，先展示受影响部分并取得用户确认，其他已确认内容继续维护。移动和改名保持文档身份；拆分分配子文档身份，合并保留旧身份定位，同时更新索引和内部链接并支持撤销。

大纲与索引共用一个可读入口，记录主题目的、适用对象、简短摘要、计划章节/路径、相关主题和补全状态；入口名称可按用户要求调整，不额外维护两份重复目录。没有正文的项目显示为“待补充”计划项，可展示拟定路径，但不提供指向不存在文件的打开链接，也不计入已有知识。正文实际保存后，才将该项关联到真实文件。Agent 负责语义组织，宿主负责验证路径、文件存在性、版本和链接；程序检索索引可以从已发布内容重建，不由业务关键词规则决定目录。

每篇在索引中提供简短摘要，正文按内容与用户要求组织，可采用调研、时间线、步骤、对比、规则等不同文体，不强制相同章节。引文与原文链接收在文末或折叠区，默认不显示内部 ID、hash、读取字节数。分组已确认、文件已生成、内容已核验是不同状态，不能相互替代。

设计与资产主题优先将 Canvas 的受控文本、正式稿件说明和页面关系整理为库内文档，记录用途、对应功能和采用版本。选定稿件和图片形成库内资产副本；来源身份用于说明导入版本，后续源变化不暗中替换已归档资产。图片二进制尚不能解析时，明确列为“尚未解读”，不把文件名猜测当作视觉结论。只有明确关联的资产进入目录，不罗列整个原项目图片目录。

篇幅以可独立理解和引用的知识对象为准；同一主题下的多个客户、阶段、并行方案可以各有正文，不能仅因主题相近就合并。初版优先清楚且完整的说明，细节较多时拆成子文档并保留入口，不把工具的一次提交上限当作项目结构。

## 文件存储与 Obsidian 兼容

知识库以普通文件夹作为可独立打开的库根，使用可读文件名、UTF-8 Markdown、真实附件和标准 Markdown 相对链接。库根与当前项目关联，拟用路径在分组清单中展示并遵循用户要求与授权范围；不能将已有同名目录直接认领或覆盖。用户可以在文件管理器或 Obsidian 中打开同一份文件，无需 DutyDeck 导出或运行转换服务。正文与已归档附件是权威内容，当前内容不再以内部条目 ID/版本目录中的 `content.md` 作为唯一存放形式。

默认生成的文档与图片引用使用标准相对链接，不依赖专有协议或插件。Obsidian 的设置目录由 Obsidian 管理，DutyDeck 不改写，也不作为知识来源。此处承诺普通 Markdown、目录、附件及基础链接的互通；Obsidian 专有查询、插件语法与图谱不作为首版互通前提，未经验证的专有语法不能宣称已兼容。

| 数据 | 作用与保存规则 |
| --- | --- |
| Markdown 正文、大纲/索引入口、附件 | 用户可直接阅读和编辑的实际文件；完整拷贝库根后，标准库内链接仍可使用 |
| 搜索分块、摘要缓存、文件定位缓存 | 可从当前文件重建；缓存缺失不阻止正文阅读，也不成为覆盖磁盘内容的依据 |
| 分组确认、来源证据、生成进度、历史与撤销记录 | 需保留的持久元数据，继续使用 JSON/JSONL 和原子写；不能在重建搜索索引时丢弃或从正文猜测恢复授权 |

持久元数据和历史与用户正文分开保存，完整备份同时包含它们；纯文件拷贝至少保证正文和库内附件可读，不意味着跨项目自动继承授权或完整历史。文档身份可以通过轻量元数据保留，不要求用户维护索引才能读写文件；外部新建的普通 Markdown 即使没有身份字段也可读取并登记。重名、重复身份或移动来源有歧义时不能按文件名猜测合并，用户的其他元数据字段应予保留。

外部编辑按以下规则同步：

- **新增或修改：** 当前磁盘内容优先，监听合并短时连续事件，文件稳定后只刷新受影响项。关闭期间的变化在重新打开知识库时补核对，不每轮对话全量扫描。用户新建文件可以被读取，但不自动等同于已核验结论，也不自动确认新的 Agent 生成范围。
- **并发保存：** Agent 写入前同时核对已读版本与磁盘内容版本；发现外部修改后拒绝用旧内容覆盖，重新读取并保留人工更改。外部编辑器不参与 DutyDeck 的锁，原子写本身不能替代冲突检测；无法可靠合并时保留候选及当前文件。
- **改名或移动：** 库内能够可靠识别为同一文档时保留身份，更新目录索引，按受控版本修订受影响的库内链接。无法识别时按缺失/新增处理并提示关联问题，不错误合并。用户修改后的目录成为维护依据，Agent 不自动改回旧路径。
- **删除：** 经核实文件不再存在时，从当前检索结果移除并标明受影响引用，不因旧缓存、大纲或生成队列自动复活。已有历史提供恢复入口，恢复由用户选择；编辑器临时替换文件引起的短时删除不立即当作最终删除。

选定资产以原格式复制归档，正文以相对路径说明用途与采用版本。文件能够保存或预览，不等于 Agent 已理解其内容；解析能力不足时继续标明覆盖状态。

## 两步建立流程

用户显式要求“建立知识库”或重建其范围时，使用以下两步。确认点位于分组清单之后；第二步内先生成大纲，再补全正文，不默认增加一次大纲审批或逐篇审批。

### 第一步：扫描分析，确认分组信息清单

从已授权项目范围的文件、既有项目记忆、当前用户指令及可用的受控来源获取材料清单，按需要读取代表正文。技术项目可补读 README、声明文件和关键代码，非技术项目不要求这些文件。先理解内容再提出分组，不能把文件夹名或文件清单直接当成知识。保留覆盖进度，区分已发现、已读、尚未读取和能力暂不支持的来源。

向用户展示一份简明清单，每组说明“准备整理什么、已有依据、缺少什么、预计产出什么”。例如下表仅演示清单的表达方式，分组名称、数量和产出类型均由实际项目决定：

| 建议分组 | 准备整理的信息 | 已有依据与覆盖情况 | 缺口 | 预计产出 |
| --- | --- | --- | --- | --- |
| 活动目标 | 面向谁、要达到什么结果 | 已读需求简报与本轮用户说明 | 成功指标待定 | 目标说明、评估标准 |
| 执行安排 | 排期、分工和资源 | 排期表已发现，正文尚未解析 | 负责人尚未核对 | 执行计划 |
| 客户约定 | 已确认要求与偏好 | 已读项目记忆中的相关段落 | 有一处历史要求需核对 | 合作约定 |

用户可以增删分组、改名、合并、调整归属和优先级，也可以只确认选中的部分。明确确认当前清单后才进入第二步；沉默、超时、切换会话或 Agent 自己表示“已确认”都不算确认。确认只确定整理范围与组织意图，不代表所有来源已读完、所有结论已核实，也不扩大项目或历史会话读取权限。

这一步允许保存扫描缓存、清单草稿和待处理进度，不能提前发布知识库大纲、创建计划正文、迁移旧记忆或搬动原资料。完全空项目先说明已知身份和具体缺口，让用户补充目标或给出分组要求，不猜测行业并套模板。

### 第二步：按确认清单生成大纲，再分批补全文件

1. **保存大纲。** 把已确认分组细化为目录、文档目的、适用对象、拟定章节、材料关联和补全顺序，保存到知识库的大纲/索引入口。先展示结构与待补项；各文档实际生成前不创建批量空 Markdown，也不伪造可打开的正文链接。用户明确只要求大纲时，在此完成任务，不擅自续写正文。
2. **按大纲选材料。** 优先读取当前文档需要的依据，同时继续处理确认范围内新增、变化和首次未审材料；不因完成少量文件就宣称完成全项目。代码按语义问题选读，图片和稿件按可用解析能力处理。接口细节由工作台呈现，知识库保留业务语义和入口。
3. **综合并写入正文。** 当前 Agent 调用知识维护 Skill，将同一对象和适用范围的材料整合成可独立阅读的文件，实际保存到对应目录。不同对象、阶段或未决方案保持区别；假设、反证、备选与阶段结果可保留并说明状态，不能强制写成已确认结论。资料不足的章节明确待补，不能为填满大纲编造内容。
4. **同步状态与索引。** 每个文件成功保存后更新对应大纲项及链接，区分已生成、部分完成、待材料和失败；文件存在不等于内容已确认。中断、预算不足或重启后从已有进度继续，已完成且未变化的内容不重复生成。只报告真实保存结果和仍缺的内容，不使用虚假的全库完成百分比。

### 后续维护与范围变化

用户已确认的范围和组织方式作为后续维护依据。普通对话中的稳定需求、决定、偏好、纠正及有后续价值的探索结果，在该范围内直接更新对应正文；不为每句话建卡片，也不重新走整库确认。已有知识库的“更新”默认增量执行第二步；首次建立、用户要求重分组或发现范围外的新主题时，展示新增/变更部分的清单供确认，已确认部分可继续。

尚未有确认清单时，对话线索保留在现有可恢复的待整理记录中，供后续清单使用，不借自动维护绕过首次建立的确认点；未完成知识库建立不影响当前对话继续。用户明确的最新纠正仍需在任务上下文中可见，不能因尚未归档而沿用旧决定。

分批执行使用当前 Agent 的模型和现有队列，无独立模型设置或递归后台 Agent。确认后默认沿大纲继续补全；用户可暂停、改大纲或指定先补某一部分，继续时只恢复仍在授权范围内的未完成项。用户对清单的修改与继续指令可以一次完成，无需修改后再机械要求确认第二次。

## 来源范围与增量更新

- 默认材料为正式项目文档、用户要求、项目声明、明确关联的设计资料和稳定项目记忆；接口工作台只提供必要业务背景和受控入口。依赖、构建缓存、锁、测试临时输出、工具运行记录不进入默认提炼集合。
- 不建立全项目每个代码文件和每张图片的知识卡片；必要时通过现有文件工具定位材料，生成库内正文或导入选定资产。原文件保持原位，来源索引仅负责定位与变化检测。
- 文档以稳定主题身份更新；依据身份独立保存，用于去重、拒绝防复活及判断过期。不能把“引文 hash”同时用作主题身份。
- 来源变化只将受影响主题标为待更新。下一次更新处理已确认范围内新增、变化、尚未审阅的材料及相关主题，复用既有处理水位，避免遗漏首次未读且以后未变的材料，也避免整库重新提炼。源文件删除或不可用时，已经整理的库内正文继续可读，来源状态单独提示，不把自己的文档一并隐藏或清空。
- 新对话先读紧凑概览和主题索引，再按任务读取相关章节；不固定注入全部正文。

## 如何接入现有实现

复用现有项目身份、原子提交、来源校验、读取预算、版本和撤销能力。新增稳定主题定位及按预期版本更新主题的最小合同；继续由 Skill 负责选择材料与组织语言，宿主负责校验与写入。无需新增数据库、向量服务或维护调度系统。

分组清单需要项目归属、稳定分组身份、范围/排除项、修订版本与真实用户确认记录。宿主将确认绑定到用户看到的具体版本；陈旧清单回执不得确认新分组。第二步的写入验证当前确认范围、大纲版本与运行状态，暂停、撤销或移出范围后的迟到结果不能发布。大纲可以在已确认范围内细化而不重复审批，扩大范围则更新清单并确认受影响项。复用现有原子写与进度记录保存确认和执行水位，不能只靠 Skill 提示词约束先后顺序。更新清单不自动删除此前已生成的文件。

旧 `KnowledgeCategory` 七类枚举、提交工具必填的封闭 category、UI 固定分类和 scanner/organizer 关键词归类必须解除对业务组织的限制。共享类型、工具/IPC、持久化迁移、UI 与检索同步适配，不能只改文件树；历史分类必要时仅作为兼容元数据，不决定新目录或限制文档类型。技术性的来源类型、操作状态与权限校验继续保留。

最小文档合同为 `topicKey + relativePath + title + summary + Markdown 正文 + 来源引用列表 + revision`。`topicKey` 标识可独立引用的知识对象，不采用有限行业词表；同主题的不同对象或并行方案可各有身份。`relativePath` 对应库内真实文件夹和可读文件名，标题或归档路径变化不改变身份。大纲中的计划项在正文生成后关联该身份；计划状态与正文的依据/确认状态分别记录。库内当前 Markdown 文件是唯一正文编辑入口，历史版本和检索索引是辅助数据。现有存储适配此合同，不能只给旧哈希版本目录加一个虚拟文件树。写入必须带读取时的 `expectedRevision`；发生并发或人工修改时拒绝覆盖，Agent 重新读取后再提出更新。正文和引用均未变化则零写入。来源变化通过引用列表找出受影响文档，标记待核对即可，首版不另建关系图引擎。

现有 6 条知识先作为有来源的材料列入分组清单；用户确认后归入对应大纲，新主题成功保存后才将旧碎片从默认目录收起，保留历史与撤销。未确认或生成失败时原知识仍可读，不直接删除旧知识或原项目资料。旧来源索引无需继续作为主要阅读界面，也不需要先删除所有缓存才能使用新方案。

当前实现仍将知识正文放在 `.proma/knowledge/entries/<id>/revisions/<revision>/content.md`，记忆固定从工作区 `memory/` 读写，接口来源适配器仍能提供接口正文。重构需将可读目录中的当前 Markdown 作为权威正文，内部版本文件只承担历史用途；同步调整来源扫描、文件监听、检索、编辑器和 Agent 写入入口。知识库自身文件不能再作为原始项目材料被循环提炼，外部编辑由知识库文件同步处理。这些边界必须随重构一并调整，不能仅修改界面名称或 Skill 提示词就宣称完成。

## 记忆纳入同一知识库

项目记忆作为知识的一种内容，进入适合该项目的主题文档：已确认决定与理由、项目约束、协作偏好、用户纠正及可复用经验。相关事实已经存在于某篇正文时，就地更新该文档，不再自动向独立 memory 文件复制一份。记忆不要求固定的“记忆”文件夹，目录同样由项目实际需求决定。

用户只需使用同一个知识库入口；普通对话和显式“记住”请求走同一写入、版本及检索路径。新会话读取紧凑索引，再按任务取相关主题，项目必要约束优先；待处理的明确纠正需要可检索的增量记录，不能在正文合并完成前静默沿用旧结论。原始对话仍由会话存储管理，不把整段聊天归档为长期记忆，也不把 Agent 建议当作已确认决定。

迁移时先将旧 memory 的可整理内容纳入清单预览，用户确认相关范围后保留来源与原文件备份，将有效内容合并到库内文档；成功后切换该工作区的读写入口，旧路径作为只读兼容入口或迁移记录，不继续自动双写。迁移与人工改动冲突时保持旧入口可用，不删除或覆盖原件。迁移可撤销；回退也必须保留迁移后的新增内容。已有跨项目通用偏好仍遵守原有作用域，不能因界面统一而向其他项目暴露项目私有记忆。

实现需同步调整记忆工具、提示词、维护 Skill、旧会话恢复与检索，统一指向库内唯一正文，并保留现有受限运行模式的读写边界。AGENTS.md 仍通过现有授权路径生效；知识文档中的规则建议不自动取得执行权限。

## 接口文档归接口工作台

接口工作台拥有接口定义及其文档视图，知识库不创建第二套接口说明文件。知识库可解释“订单提交后触发支付”等项目业务流程，并链接到对应接口；参数、请求示例、响应字段等内容统一在工作台查阅和维护。

文档视图直接从工作台保存的接口名称、说明、方法、地址、参数、请求体及明确保存的示例生成；定义更新时文档同步更新，不依赖每次让 Agent 重写全文，也不为打开文档自动发送请求。当前定义尚不具备完整字段说明与响应契约，缺失信息应标明待补，不能把一次真实响应或推断当作正式契约。运行响应作为示例时需脱敏并标明采集时间。

当前工作台已具备请求定义和响应展示基础，但尚无完整的文档阅读视图；自动文档呈现属于待实现内容。重构时调整知识库的 API 来源适配器，只保留受控入口及必要业务背景。原有接口相关知识先提取仍有价值的业务说明，并保留历史；接口详情有可用的工作台入口后再从知识库默认目录收起，避免迁移中失去查阅渠道。Canvas 继续拥有可编辑创作源，知识库保存整理后的说明及选定版本的资产。

## 开销与验收

开销主要来自当前 Agent 的必要阅读与提炼。第一步有界扫描与代表正文阅读复用已有缓存，先让用户排除不需要的范围，减少无效生成；第二步在写入前核对来源版本，沿大纲分批处理新增、变化和未审材料，避免重复全扫与每轮重规划。外部文件监听复用既有能力，合并事件并增量刷新索引，不因普通保存自动启动全库模型提炼。UI 默认加载分组、大纲状态和主题摘要，正文与引用按需展开；新会话只加载相关内容。统一记忆减少重复写入和重复上下文，接口文档在本地从定义派生，无需额外模型调用。不新增数据库、向量服务或独立后台 Agent。

关联影响集中在建立入口与 Agent 交互、清单确认及恢复、大纲与主题写入/索引、文件监听和编辑冲突、现有 memory 的读写/迁移，以及接口工作台文档视图和 API 来源适配器。项目授权、Automation/Collaboration 和 Canvas 的原始内容所有权保持既有边界；任何调用方都不能绕过已确认范围的写入门禁。宿主发起的文件与索引变更按可恢复流程发布；外部文件变化可能先于索引，须以磁盘版本核对并补齐索引，不能依赖不存在的跨应用事务。

验收以使用结果为准：

1. 首次请求建立时先收到可调整的分组信息清单，包括已有信息、依据、覆盖情况、缺口与预计产出；未确认时不生成知识库大纲或正文、不迁移旧记忆，已有知识继续可读。
2. 确认选定分组后先看到真实保存的大纲，再逐项生成正文及目录；未生成项标明待补，无悬空文件链接；关闭 DutyDeck 后也能找到已保存的真实文件。同一对象和范围的多份材料形成连贯说明，重复更新不增加同义文档。
3. 用户纠正一个已确认决定后，对应文档更新，新对话能检索到；旧依据可追溯。
4. 修改工作台的一项接口定义，文档视图随之更新；知识库只保留业务说明和入口，不产生参数/响应文档副本，不为此重跑全库或自动发送请求。
5. 原始代码与资产不被搬走；选定资产可复制归档。旧 memory 保留可恢复原件，迁移成功后读写切到同一知识正文。内部锁及版本文件不出现在业务改动列表。
6. 已保存文档即使待核验也能在知识库中找到；Agent 自动引用时仍明确状态。
7. 存量迁移可预览、可撤销，真实项目提炼质量需另行验收，不能用替身测试宣称通过。
8. 仅依据用户明确指令也能创建相应知识文档；原始材料暂时不可用时，库内已整理正文及已导入资产仍可阅读。
9. 策划、研发及混合项目均能提出符合材料的分组；确认旧七类以外的自定义组织后，提交、重启、检索和增量更新均保留用户要求，不发生关键词重分类或固定章节回填。
10. 对话中明确要求记住一项项目决定后，同一知识文件更新，新会话可检索；原 memory 与知识库不重复写入。迁移失败、并发修改、回退及旧会话恢复均不丢失已有内容或扩大访问范围。
11. 用户要求拆分或重组目录后，正文、索引和内部引用一致，旧入口仍可定位历史，并能撤销整理；重复扫描且来源未变时零正文写入。
12. 用户仅确认部分清单时只生成相应内容；修改清单后旧版本确认不生效，暂停或移出范围后的迟到结果不发布；已有文件不因修改清单而自动删除。
13. 生成中断或首次预算不足后可继续未完成项，即使剩余来源没有变化也不会遗漏；已完成且未变的正文不重复生成。清单确认不把缺少依据或未决内容升级为已确认知识。
14. 多客户与 A/B 方案可分别查阅和检索；用户要求时间线或操作步骤时保留相应文体。无材料项目不生成虚构主题，用户补充目标后再提出分组清单；明确只要大纲时不续写正文。
15. 已确认范围内的日常对话沉淀和内容补全不逐项重新审批；新增范围先确认受影响清单，范围内自动整理保留用户固定结构、文档身份关系和可撤销能力。
16. 关闭 DutyDeck 后可用 Obsidian 打开库根，阅读生成的 Markdown 与图片相对引用；整体复制正文和库内附件到另一目录后基础链接仍有效。互通需真实应用验证，不能仅用扩展名相同证明。
17. 外部修改、新建、改名和移动后，DutyDeck 增量反映当前文件；并发修改不会被 Agent 旧版本覆盖。库内删除不会因大纲或缓存自动重建，外部编辑器的临时替换保存不会被误判为永久删除。
18. 重建搜索缓存不丢失正文、附件和持久确认记录；无元数据的新文档仍可读，重复身份不误合并。知识库文件和 Obsidian 设置不反复进入原始资料提炼范围。

## 此前错误修复验证

- 6 条知识均已保存，本轮未清空或重建项目资料。重复引文按来源、版本、引文正文共同识别，完全重复引文只显示一次；目录刷新保留旧结果并显示加载状态。
- `.proma/knowledge` 内部目录从 watcher、回合采集和历史快照展示中排除；其它 `.proma` 文件、用户源码及测试文件保留，不用项目专属临时文件名黑名单掩盖改动。
- 64 项相关测试、全仓 8 个工作区类型检查及主进程构建通过。Dev 已加载新代码；真实 Electron 中打开含 7 段引文的 SDK 知识，清除旧控制台记录后未再出现重复 key 警告。
- 上述验证仅覆盖错误修复；本方案的两步建立流程、动态目录、可外部编辑的文件存储、增量修订、记忆统一和接口文档视图尚待实施，不能将此前测试结果作为新方案已完成的证据。
