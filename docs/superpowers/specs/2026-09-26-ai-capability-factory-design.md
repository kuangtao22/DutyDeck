# AI 能力工厂（AI Capability Factory）设计草案

> **状态：草案，未实施。** 本文只定义边界与产物契约，不包含任务级实施步骤；任务拆分等本文确认后再落到 `docs/superpowers/plans/`。

**目标：** 在 DutyDeck 内提供一个与「运维」「接口」同级的模块，用于编排多步 Agent 工作流、试跑、评测、迭代，最终导出一个**自包含的资源能力包**；用户自行把该能力包交给关联项目接入使用。

**核心定位：** DutyDeck 是这个工厂的 IDE，**不是运行时**。工厂的唯一交付物是能力包文件，消费方项目自带运行时。

---

## 1. 已确认的决策

| 编号 | 决策 | 影响 |
| --- | --- | --- |
| D1 | 走「自包含能力包」路线，不出远程调用 | 能力包必须完全脱离 DutyDeck 运行，见第 2 节 |
| D2 | 能力包不进 DutyDeck 的 git，产物交给别的项目 | DutyDeck 侧只保留版本历史与运行记录；产物本身仍须可 diff、可校验 |
| D3 | 账号查询只是举例项目，测试用虚拟数据 | 工厂需要「工具桩（tool stub）」作为一等对象，见第 5 节 |
| D4 | 消费方 app **也在 DutyDeck 里开发**（同一个工作区/项目） | 工厂绑定当前工作区，可读该项目；草稿与运行记录全部留工作区级，不需要跨 workspace 全局存储。见第 1.5 节 |

## 1.5 使用闭环（实际交互顺序）

这是本模块的真实用法，其他所有设计都要服务于这条闭环：

1. 在 DutyDeck 打开目标 app 的项目（工作区）。
2. 打开同级的「Agent 提示词工厂」标签。
3. **与 Agent 对话**：Agent 读取当前项目（已授权项目根）的接口定义、数据模型与技术栈，据此设计工作流步骤、提示词与输入输出契约。
4. **Agent 生成虚拟接入**：把工作流声明的 capability 绑定到按真实接口字段生成的桩实现。
5. 在模块内运行，查看每一步的输入输出、工具调用与耗时（轨迹）。
6. 依据结果迭代提示词，产出新版本，与基线对比。
7. 导出能力包，交给该 app 项目接入。

**第 3、4 步必须由 Agent 从真实项目生成**，否则用户要手写契约与桩实现，成本与直接写代码相当，模块失去存在意义。这两步是"工厂"相对于"提示词编辑器"的全部价值所在。

### 虚拟接入的两种做法（必须选后者）

| 做法 | 结果 |
| --- | --- |
| 只要跑通：桩返回任意假数据 | 流程不报错，但字段名与真实接口不一致，真实接入时提示词全部要返工 |
| 按真实契约生成：桩的字段名/类型/嵌套结构取自项目中真实的接口定义 | 工作流在真实接入时不需要改提示词，工厂里的评测结论可迁移 |

### 工作台形态：对话为主，图为辅

驱动方式是 Agent 对话，因此模块主界面应是**对话 + 轨迹 + 结果**，步骤关系图只是可视化辅助，不应让人从空白画布开始拖节点。这与 Canvas 的分工正好相反（Canvas 以人为中心的拖拽作图为主）。

**由 D1 推导出的硬约束（本设计的骨架）：**

能力包不得引用任何 DutyDeck 内部概念，具体包括：

1. 不得出现 `canvas_*`、`Read`、`Bash`、`api_*` 等 DutyDeck 工具名 → 工具需求必须抽象成 capability 声明（第 5 节）。
2. 不得依赖 DutyDeck 的系统提示词注入、`AGENTS.md` 解析、Skills 装配、权限模型、工作区隔离 → 执行语义必须由 spec 自带（第 4 节）。
3. 不得假设消费方与 DutyDeck 用同一个模型或同一套默认参数 → 模型必须固化在包里并允许覆盖（第 7 节）。
4. 不得假设消费方知道步骤之间怎么传数据 → 输入输出契约与数据映射必须显式声明（第 3 节）。

## 2. 能力包（Capability Package）

唯一的交付物。一个 JSON 文件（可选带同级 `prompts/` 目录），自包含、可 diff、带版本。

沿用仓库已有先例：`packages/shared/src/types/api-workbench-sharing.ts` 的集合快照——`kind` 标记 + `version` + 严格字段白名单解析 + 导出时清空秘密。能力包沿用这套纪律。

```jsonc
{
  "kind": "proma-ai-capability-package",
  "packageVersion": "1.0.0",        // 本包自身的语义化版本，每次导出固化
  "specVersion": 1,                 // spec 格式版本，消费方按它选 runner
  "name": "novel-character-extraction",
  "description": "从小说章节文本中抽取角色表与人物关系",
  "exportedAt": 1790000000000,

  "inputs": { /* 调用方必须提供的字段 schema */ },
  "outputs": { /* 调用方会拿到的字段 schema */ },

  "steps": [ /* 见第 4 节 */ ],

  "capabilities": [ /* 本工作流需要消费方绑定的外部能力，见第 5 节 */ ],
  "modelSlots": [ /* 本工作流需要的模型槽位，见第 7 节 */ ],

  "acceptance": { /* 冻结的评判指标定义：评测器类型 + 字段权重 + 幻觉判定，见第 6 节 */ },
  "evidence": { /* 导出时的评测基线，见第 6 节 */ }
}
```

**结果约束的位置：** 每一步的 `outputSchema` + `strictness`（第 5.5 节）随 `steps` 一起进包——消费方的 runner 必须同样执行强校验，否则「工厂里合法」与「产品里合法」是两套标准。

**`acceptance` 与 `evidence` 的地位：** `acceptance` 是**冻结的指标定义**（不是提示词文字），`evidence` 是「这个包在工厂里跑出过什么分数」的凭证，不含原始数据集正文。消费方改提示词后可以用同一份 `acceptance` 重新评测、与 `evidence` 对比，判断自己是否把它改差了。指标定义不冻结，这个对比就不成立。

**不随包导出的东西：** 评测数据集正文（可能很大，也可能含消费方数据，按 D2 不进产物）、DutyDeck 运行记录、会话 ID、工作区路径、任何凭据。

## 3. 输入输出契约与数据映射

每个工作流必须声明三样东西，缺任一项则不合法：

- `inputs`：调用方传什么。字段名、类型、必填性。
- `outputs`：调用方拿到什么。必须是某个步骤输出的映射（或聚合）。
- `steps[].input`：每一步的输入从哪来。来源只有三类——工作流输入、上一步输出、常量。

**为什么不能省：** 没有 `inputs`，消费方接不上自己的数据；没有 `outputs`，消费方只能拿到中间过程的原始文本；没有显式映射，步骤间的数据流只能靠消费方猜，同一个包在不同项目里会跑出不同结果。

---

## 4. 执行语义（spec 的核心）

因为 DutyDeck 不是运行时（D1），**执行语义必须由 spec 定义**，而不是由 DutyDeck 的 Agent runtime 定义。这是本设计里最需要谨慎的部分。

最小语义集合：

| 概念 | 定义 |
| --- | --- |
| 步骤类型 | `llm`（单次模型调用）、`tool`（调用一个已绑定的 capability）、`extract`（把上一步输出按 schema 结构化） |
| 数据流 | 每步声明输入来源；不声明隐式上下文传递 |
| 提示词 | 每步内联完整提示词正文（含变量占位符），不引用外部 Skill |
| 重试 | 每步声明最大重试次数与失败判定（模型错误 / schema 校验失败） |
| 终止 | 任一步在重试耗尽后失败，则整个工作流失败并返回已完成的步骤轨迹 |
| 确定性 | 步骤按声明顺序串行执行；v1 不支持并行、分支、循环 |
| 错误 | 返回结构化错误，不抛异常给消费方；失败步骤必须可见 |

### 参考 runner 是必须的

只有 spec 没有 runner 时，每个消费方项目会各自解释 spec，结果是「在工厂里通过 ≠ 在产品里通过」——工厂的评测分数不再能预测生产行为，整个模块退化成「带图的提示词编辑器」。

因此 v1 必须交付一个**参考实现**，形态可以是：一个不超过几百行的、只依赖 fetch 的 TypeScript/JS 模块，随能力包一起交给消费方（或者作为独立小包发布）。它的职责只有一个：按 spec 语义执行，保证各处行为一致。

代价评估：这是本设计里唯一不可省略、又无法靠 DutyDeck 现有代码直接复用的新增件。它的复杂度上限应当被严格限制在 v1 语义集合内——每增加一种步骤类型或控制流，runner 的兼容性负担都会成倍增长。

## 5. 能力声明与绑定（工具抽象）

工作流需要外部能力时（账号查询的举例项目需要「调用账号查询 API」），**不能**在步骤里写具体函数名，而是声明一个抽象能力：

```jsonc
{
  "capabilities": [
    {
      "id": "query-account",
      "description": "按账号标识查询账号状态",
      "inputSchema": { /* ... */ },
      "outputSchema": { /* ... */ },
      "sideEffect": "read"            // read | write | irreversible
    }
  ]
}
```

消费方在接入时把 `query-account` 绑定到自己的实现。步骤里只写 `{ "type": "tool", "capability": "query-account" }`。

### 工具桩（由 D3 推出）

迭代期消费方的实现往往还不存在，或者测试必须用虚拟数据。因此工厂内需要**工具桩**作为一等对象：用户为某个 capability 定义一个返回固定/规则化结果的桩，工作流据此可以完整跑通。

没有工具桩，账号查询这类工作流在接入前根本无法评测——而它恰恰是最需要提前迭代的那类。

### `sideEffect` 的用途

它不是安全机制（D3 已确认测试用虚拟数据），而是**评测与文档的信号**：让消费方接入时一眼看到这个包会不会写数据，也让工厂在展示轨迹时能标注「这一步改动了外部状态」。

---

## 5.5 结果约束（Output Constraints）

结果约束是**机器可判的硬性要求**：必须是合法 JSON、必须包含哪些字段、字段必须是哪几个枚举值之一。它和评判指标是两件不同的事，见第 6 节。

### 约束必须结构化，不能只写在提示词里

| 做法 | 结果 |
| --- | --- |
| 只在提示词里写「请返回 JSON，包含 name 字段」 | 模型会漂移；无法校验；失败时定位不到是哪个字段 |
| 声明结构化 schema，由运行时强校验 | 可精确报错；可按字段重试；评测时能统计格式合规率 |

每个步骤（至少是工作流输出步骤）声明：

```jsonc
{
  "outputSchema": { /* 字段名、类型、必填、枚举 */ },
  "strictness": "strict"              // strict：不合法即判该次运行失败并按策略重试
}                                     // lenient：不合法也返回，但标记为 invalid
```

`outputSchema` 一份定义驱动三件事：①自动生成提示词里的格式说明（不手写两份）；②运行时强校验；③评测器的输入（知道该比对哪些字段）。

### 约束从项目里读，而不是让用户口述

「status 必须是这三个枚举值之一」这类约束，通常已经存在于项目的数据模型、类型定义或接口定义里。Agent 应当从当前项目读出它们，而不是让用户凭记忆复述——这和第 1.5 节「虚拟接入按真实契约生成」是同一个机制：

**读项目 → 生成契约 → 生成结果约束 → 生成桩 → 评测**

这条链路自洽，也是工厂相对于手工配置的核心效率来源。

## 6. 评测

### 约束失败 ≠ 质量差（必须分开统计）

这是最容易踩的一个坑：把「必须返回 JSON」当成一个评分项，结果一次格式错误把整条分数拖垮，掩盖了真实的抽取质量问题。

正确做法是分成两层：

| 层 | 判定 | 含义 |
| --- | --- | --- |
| 约束（constraint） | 二元：合法 / 不合法 | 这次运行是否**有效** |
| 指标（metric） | 数值 | 这个提示词版本**好不好** |

不合法的运行标记为 `invalid`，**不计入准确率统计**，单独报告 `invalid rate`。并且必须同时报告有效样本数：如果一个提示词 40% 的运行返回非法 JSON，那它剩下的 60% 算出的准确率没有意义，此时应拒绝给出准确率结论，而不是给一个漂亮数字。

### 评测器插件化，不做通用评分

不同场景的评测范式不同，试图用一套评分覆盖会导致两边都不够用：

| | 抽取类（小说角色） | 工具调用类（账号查询） |
| --- | --- | --- |
| 形态 | 批处理、离线、结构化抽取 | 工具调用、实时、有状态 |
| 好的定义 | 字段级精确率 / 召回率 / 幻觉率 | 任务完成率 + 工具调用正确性 |
| 验收依赖 | 人工 gold 标注数据集 | 轨迹断言 + 外部状态检查 |
| 典型失败 | 编造不存在的角色 | 调错参数、漏一步、顺序错 |

结论：上层（定义、版本、运行记录、对比、成本、导出）通用；下层按场景类型注册评测器。v1 只做 `extraction` 一种。

### 抽取类评测的两条硬规则

1. **精确率与召回率必须成对出现。** 多提取 20 个角色、其中 8 个是编造的提示词，只看命中数会显得更优。数据集必须包含负样本（文中不存在的相似名字），单独统计幻觉率。
2. **单次运行不构成结论。** 同一提示词重复 N 次的结果会不同，比较必须看分布而非单点。模型、温度、数据集版本随结果一并冻结，否则分数无法归因。

### 评判指标的生成纪律：Agent 提议 → 人确认 → 冻结

指标的**来源**应当由 Agent 结合对话与当前项目定制生成（这是对的，指标必须因场景而异），但指标的**算法**不能由 Agent 每次自由发明。三条纪律：

1. **Agent 生成的指标必须落到工厂已有的评测器类型上**（v1 只有 `extraction`：字段级精确率 / 召回率 / 幻觉率），而不是发明「1–10 分质量分」这类自由评分。自由评分不可复现、不可比较，且极易被模型自评刷高。
2. **Agent 可以提议的是「哪些字段重要、各自权重、哪些算幻觉」，不是评分代码。** 否则 A 版本和 B 版本的指标不同，你无法判断提示词改好了还是指标放宽了——**跨版本比较会整体失效**。
3. **指标一经确认即冻结**，与工作流版本绑定并随能力包导出。之后迭代提示词的整个过程中指标不动；要改指标就作为一个显式的、独立于提示词迭代的动作，并重算基线。

第 2 条是最容易忽略、代价最大的一条：指标允许每次重新生成，等于把「比较」这件事本身破坏掉了。

### 指标里的项目来源

指标的一部分可以直接取自当前项目：数据模型里的枚举值、接口定义里的字段约束、类型定义里的可空性——这些都能转成「必须满足 / 必须属于某集合」的检查项。这既减少了用户口述，也保证了约束与真实 app 一致。

### 轨迹是编排的唯一增量

值得为「多步编排」付出复杂度的唯一理由是：能看到每一步的中间输入输出与工具调用。失败往往发生在中间步骤而非最终输出，只看最终结果无法定位。

轨迹同时是定点重跑的基础：第 N 步之前的事实未变时，只重跑第 N 步及下游，不重跑整链。这是迭代速度的主要来源。

## 7. 模型槽位

能力包里固化模型标识与参数（温度、最大 token），同时允许消费方覆盖。理由：工厂里的评测结论只在同一模型下成立；不固化就会得出「A 提示词更好」然后换个模型结论反转，而没人知道原因。

`modelSlots` 用于一步需要多个模型时（例如便宜模型做初筛、强模型做归纳）。

---

## 8. Agent 操控面与权限

Agent 可以：创建草稿工作流、修改提示词产生新版本、跑评测、读运行记录与轨迹、分析失败案例。

Agent **不可以自主执行导出/发布**。理由：能力包一旦被外部项目接入，就等于改变了那个项目的行为；提示词是可执行内容，这种改变在代码 review 中不可见，比 Agent 自主提交代码更隐蔽。导出必须由人显式触发。

同理，工作流的 `inputs` / `outputs` 一旦随包交付，修改按破坏性变更处理：出新 `packageVersion`，不覆盖旧版本。

### 成本控制

评测即真实模型调用。必须内建：单次评测预算上限、并发上限、结果缓存（提示词版本与输入均未变则复用，不重跑）、分层数据集（冒烟集用于迭代，全集用于验收）。

## 9. 与现有能力的边界

| 对象 | 边界 |
| --- | --- |
| Skills（`default-skills/*/SKILL.md`） | Skill 是给 Agent 自己判断何时使用的知识，人读的 markdown，无契约、模型自选。工厂产出的是机器显式调用的确定性能力，固定输入输出。**建议**：定义真相只存在于工厂；如需给 Agent 自用，再由工厂生成一份 Skill，而不是两处各写一份。 |
| Canvas | Canvas 是用户可见、可拖拽的产物创作图，产物是文档/图片/视频。工厂是面向机器调用的能力生产线。Canvas 的 workflow run（持久 journal、预算、幂等恢复）可作为**执行引擎**复用，但不把工厂做成第二个画布。 |
| 接口工作台 | 两者模式同构：用例 + 断言 + 运行记录 + 与基线对比。接口工作台的 B7–B11 已在真机验收过这套模式，评测层应借鉴甚至抽取公共部分，区别仅在传输层（HTTP vs 模型调用）。 |

## 10. 模块落地清单（同级模块）

「同级」在本仓库有确定含义：`WorkspaceComponentTab` 的一个值（`apps/electron/src/renderer/atoms/agent-atoms.ts:771`），挂在 Agent 右侧工作台标签栏。

| 层 | 位置 |
| --- | --- |
| 模块标识 | `renderer/atoms/agent-atoms.ts` 的 `WorkspaceComponentTab` 与 `WORKSPACE_COMPONENT_TABS` |
| 入口标签 | `renderer/components/agent/SidePanel.tsx`（「运维」「接口」同级映射） |
| 主进程服务 | 新建 `main/lib/<module>/`，参照 `main/lib/api-workbench/` 分层 |
| IPC 四层 | shared 常量/类型 → `main/ipc.ts` → `preload/index.ts` → renderer |
| Agent 操控 | `<module>-agent-facade.ts` + `<module>-agent-tools.ts`，参照 `api-agent-facade.ts` |
| 准入 | 参照 `apiWorkbenchManualDenialReason`、`server-ops-agent-access-session-guard` |
| 引导页 | `renderer/components/onboarding/SelfBuiltModulesPage.tsx`（现有四张卡片） |

**存储范围：** 草稿工作流、运行记录、评测结果、数据集、虚拟接入全部留在 workspace 级（沿用 `safe-file` 原子写）。因为消费方 app 也在同一工作区开发（D4），**不需要跨 workspace 的全局存储**，也不需要"已发布版本仓库"这一层；导出是显式动作，产物由用户决定放哪，DutyDeck 不接管其去向。

---

## 11. 分期

**v1（先证明闭环）**：单工作流、串行步骤、`llm` + `extract` 步骤类型、**结果约束（`outputSchema` + `strictness` + 强校验 + 按约束重试）**、`extraction` 评测器、**Agent 提议并经人确认后冻结的评判指标**、**Agent 对话驱动的建流与按真实契约生成的虚拟接入**、单一模型槽位、能力包导出、参考 runner。用小说角色提取端到端跑通「对话建流 → 虚拟接入 → 结果约束与指标定稿 → 试跑 → 评测 → 改提示词 → 对比 → 导出」。

**v1 必须区分并分别报告：** `invalid rate`（约束不合法比例）与 准确率 / 召回率 / 幻觉率（仅统计合法样本，且附有效样本数）。

**v1 的第一个任务不是模块外壳**，而是「spec 解析器 + 参考 runner + 一个冒烟用例」——先证明能力包能脱离 DutyDeck 跑起来，再建 UI。否则容易建出一个好看但产物跑不通的界面。

**v2**：`tool` 步骤类型 + 轨迹断言评测器、多版本矩阵对比、定点重跑、缓存与预算面板。

**v3**：UI 完善、从失败案例回灌成新用例、Agent 侧完整工具面。

**先做抽取类而非工具调用类的原因**：抽取类能给出客观分数，闭环是否成立一眼可验。若第一个场景就无法客观评分，后续所有设计都会建立在猜测上。

## 12. 待定与风险

1. **参考 runner 的分发形态未定**：随包附源码、独立小包、还是只给文档+伪代码。这是 v1 唯一无法复用的新增件。
2. **命名未定**：「提示词编排工厂」偏窄，容易让后续设计都向「编辑文本」偏，忽略评测、轨迹、契约、导出。候选：AI 能力工厂 / Workflow Studio。
3. **`packageVersion` 与 `specVersion` 的兼容策略未定**：spec 不兼容升级时旧消费方如何处置（拒绝加载还是降级）。
4. **数据集不随包走（D2）** 意味着消费方无法自行复现工厂里的分数，只能信任 `evidence`。这是一个已被接受的缺口，但影响「消费方改了我们怎么发现」。
5. **Agent 自主导出禁止**需要与现有审批链路对齐，参照接口工作台 B7b 的「来源盖章」与 canvas 的付费审批。
6. **Agent 读项目的边界未定**：Agent 需要读当前工作区的项目根来提取接口契约，必须复用已授权项目根的显式路径解析（`project-instruction-resolver.ts` 的边界纪律），不得恢复 cwd/祖先目录/环境式发现。读到的内容是否进模型上下文、是否可能带出凭据，需要在 v1 明确。
7. **虚拟接入由 Agent 生成的质量风险**：桩的字段名与真实接口不一致时，工作流会在真实接入时返工，而工厂内的评测全部通过——这是最难发现的一类失败。缓解方式：桩必须从项目里真实的接口定义生成（而非模型凭描述臆造），并在导出前给出"桩契约 vs 真实契约"的一致性检查。
8. **指标由 Agent 生成的自证风险**：Agent 设计的指标会倾向自己容易达到的方向，尤其当指标依赖另一个模型打分时（那个模型会给"看起来更完整"的输出高分，而更完整往往等于编造更多）。缓解方式即第 6 节三条纪律：指标必须落到工厂已有评测器类型、Agent 只提议字段权重不写评分代码、确认后冻结。
9. **约束与指标混淆的风险**：把"必须返回 JSON"当成评分项，会让一次格式错误掩盖真实的抽取质量退化。v1 必须在数据结构和 UI 上就把二者分开（`invalid rate` 与准确率分列），而不是靠约定。

## 附：本草案替用户做的假设（需确认）

| 假设 | 依据 | 影响 |
| --- | --- | --- |
| v1 只支持串行，不做并行/分支/循环 | 每种控制流都成倍增加 runner 负担 | 复杂编排要等 v2+ |
| 参考 runner 必须交付（而非只给 spec） | 否则工厂评测结果无法预测生产行为 | v1 多一份维护件 |
| 评测数据集不随包导出 | D2 与体积/隐私考虑 | 消费方只能信任 evidence |
| 模型固化在包内并允许覆盖 | 不固化则评测结论不可迁移 | 消费方换模型时需重新评测 |
| 模块主界面是「对话为主、图为辅」 | 驱动方式是 Agent 对话（D4） | 与 Canvas 的交互模型相反，不能复用 Canvas 的手动拖拽范式 |
| 桩必须按真实接口契约生成 | 否则真实接入时提示词全部返工 | Agent 需能读项目内的接口定义，见风险 6/7 |
| 结果约束用结构化 schema，而非只写在提示词里 | 提示词约束不可校验、失败无法定位 | 每步需声明 `outputSchema` + `strictness` |
| 评判指标由 Agent 提议、**人确认后冻结**，且只能落到工厂已有评测器类型 | 指标若每次重新生成，跨版本比较整体失效；自由评分易被模型自评刷高 | Agent 只提议字段权重与幻觉判定，不产出评分代码 |
| `invalid`（约束不合法）与准确率分开统计 | 格式错误会掩盖真实质量退化 | v1 数据结构与 UI 必须分列，见风险 9 |
